# 技术设计：九宫格房间内容与地形卡生命周期

状态：规划中，尚未实施。需求与验收编号见 `prd.md`，执行顺序见 `implement.md`。

## 1. 总体边界

```text
MapPositionCreate / MapWorldModel：地图布局、邻接、房间资源与坐标换算
                         │ get_window_positions / 房间激活与退出事件
                         ▼
UIMapWorldView：3×3 完整房间场景实例
                         │ 每房间 RoomContentRoot
                         ▼
RoomContentStreamer：房间内容的激活、重建、释放和索引
          │                │                     │
RoomTerrainStore       RoomLootStore       RoomBuildingStore
  地形运行状态          掉落运行状态          建筑运行状态
          └────────────────┴─────────────────────┘
                         │ 只读状态实例化
                         ▼
             Item（地形/掉落）与 BuildingView
                         │ 输入事件
                         ▼
       BoardController / WorldInteractionCoordinator / BuildingController
```

房间状态仓库是事实来源；场景节点只是可丢弃的表现。`MapWorldModel` 仍只负责地图本身，不接管地形、掉落和建筑业务。`RoomContentStreamer` 只协调生命周期与视图索引，不结算采集、库存或建筑规则。当前 `UIMapWorldView` 创建完整房间的过程不变，只增加明确的房间激活/退出通知；窗口外依旧释放节点而非保存整棵节点树。

## 2. 房间激活与坐标

每个活动房间根节点下创建一个 `RoomContentRoot: Node2D`，其局部原点就是该房间左上角。`Item` 和建筑表现以房间局部坐标挂在该根节点下。世界坐标只在边界处换算：`world = MapWorldModel.world_origin_for(room) + local_position`；窗口外状态不保存当前相机、父节点或全局坐标。`TerrainInstance.BoardPosition` 现值已经是房间内部摆放坐标，迁移时保留其语义，显示时通过房间根节点转换；掉落和建筑同样存局部坐标。

窗口更新顺序：

1. 从 `MapWorldModel.get_window_positions(center)` 得到有效坐标集。
2. 对新增坐标先建立完整房间场景、读取其 `terrain_profile`，再按需首次生成地形状态并挂载该房间的地形、掉落、建筑视图。
3. 对仍在窗口内的房间只保留原节点，局部状态更新由对应仓库信号增量同步；不重复生成、不全量重建九房。
4. 对离开窗口的房间先取消该房间未完成的输入/动画并解除视图索引，再释放 `RoomContentRoot` 和房间场景；状态仓库不清空。
5. 当前房间改变的信号仍提供给背景、HUD 和当前房间交互门禁，但不得再触发 `ClearAllCards()` 清除其他八房。

首次进入窗口即可生成该房间内容，不能等玩家踏入该房间才生成。若房间状态存在，即使地形全部采尽或掉落为空，也以“已生成”标记防止重复抽样。可重复采集的恢复时间继续用游戏总时间计算：窗口外没有计时节点运行，回到窗口时按既有 `RefreshIfReady` 规则补算。

## 3. 状态模型与唯一身份

| 状态拥有者 | 最小字段 | 变更入口 |
|---|---|---|
| `RoomTerrainStore` | 房间坐标、局部格子坐标、`TerrainData`、`BoardPosition`、占用/采集/成长/剩余次数/恢复时间、遭遇倍率 | 首次布局生成与已有地形交互 |
| 新 `RoomLootStore` | 房间坐标、单调递增掉落 ID、物品堆叠快照、房间局部最终落点、可拾取状态 | 掉落生成、拾取确认、拆除掉落 |
| `RoomBuildingStore` | 房间坐标、建筑 ID、配置资源、局部坐标、实例状态 | 放置、使用、拆除 |

视图索引统一以 `(room_pos, kind, instance_id)` 标识；地形的 `instance_id` 取局部网格坐标。不能只用局部格子坐标索引九房，否则不同房间同一格会冲突。掉落 ID 在本局内稳定；拾取时用 ID 从仓库移除，重入点击看不到第二次成功。背包拒收时不改状态。

掉落散射顺序改为“先算最终落点并登记仓库，再创建视图播放从起点到落点的表现”。落点要限制在所属房间可放置范围，并避开不可通行地形与边界；如现有散射参数没有合法落点，则采用经校验的起点附近退化位置。窗口卸载或动画中断后再进入，直接显示已登记的最终落点，不重播随机散射。原有 `BoardController.SpawnLootCards(...)` 等调用方保留兼容入口，由新房间上下文转发；建筑拆除也走同一登记入口。

## 4. 地形卡与掉落物视图、碰撞与输入

保留用户创建的 `scenes/ItemTerrian/Item.tscn` 及其 `CharacterBody2D` 根节点作为地形卡视图；新增 `scenes/Loot/Loot.tscn` 作为掉落物视图。`BoardController` 按 `BoardCardState` 选择两类预制体，两个视图分别只绑定自己的状态并保持调用方需要的 `GetTerrainInstanceOrNull`、`GetLootStackOrNull`、`RefreshView` 与交互信号协议。`BoardController` 的现有信号和当前房间查询兼容入口继续存在；新增带房间参数的查询供九房内容使用。

- 地形卡的 `Collision` 只负责实体阻挡。地形启用时使用第 6 物理层（值 `32`，与 `PlayerChar` 的碰撞掩码一致）；掉落物场景没有实体碰撞，根节点物理层与掩码为 `0`，玩家可直接走过。
- `Interaction` 仅负责鼠标命中。它作为两个视图根节点下的独立 `Area2D` 保留有效碰撞层和 `input_pickable`，用 `_input_event` / 鼠标进入离开信号统一转发点击、按下、抬起、悬停。拾取或禁用时立即关闭输入命中。
- `Visuals/PlayerView` 是视觉与排版容器，按钮鼠标过滤设为忽略，不能与 `Interaction` 争夺事件。`Collision` 和 `Interaction` 都挂在根节点，不放在动画变形的 `Visuals` 下。
- 地形卡实体碰撞会改变放置安全性。生成时需使用与现有建筑放置相同的房间边界、桥口、障碍和玩家保护范围校验，避免堵住桥或把玩家生成在碰撞内；不能改变 TileMap 本身的已有边界。

长按圆环目前尝试 `card/Icon`，而新场景图标位于 `Visuals/PlayerView/Icon`。为视图增加稳定的 `GetProgressAnchor()`，协调器从该入口取锚点，避免硬编码内部节点路径。动态方法和信号必须通过编辑器运行验证。

## 5. 拾取与动画

拾取事务顺序：先调用既有 `TryAddItemToInventory`；成功后立刻从 `RoomLootStore` 删除 ID，禁用源 `Loot` 的 `Interaction`，从房间内容根节点脱离纯视觉飞行副本到世界特效层；视觉在每帧读取 `PlayerChar` 的全局位置作为目标，结束后释放。这样跨房卸载、重复点击和角色边走边捡都不会重复结算或使已拾取物重现。失败时不动仓库或视图。

`AnimationPlayer` 提供 `Idle`（循环）与 `Hover`（短促挤压、拉伸、回弹）。`Idle` 的轨道只能是 `Visuals` 的 `scale` / `modulate` 等视觉属性，明确禁止任何 `position`、`rotation` 轨道；`Hover` 也不改根节点及两个命中节点的变换。建议默认节奏为 `Idle` 约 `1.8 s`、`Hover` 约 `0.25 s`，实际时长、缩放和颜色全部在动作配置资源中导出；这些是待实施的初始调试值，不是已上线数值。每个实例使用独立的动画资源或只读配置，避免修改共享 `AnimationLibrary` 使九房全部同步跳帧。悬停结束恢复循环 `Idle`；拾取飞行与散射拥有更高优先级并可取消，不能被悬停重启。

## 6. 配置资源

- 继续以 `RoomTerrainProfile` 的 `TerrainPool`、`MinCount`、`MaxCount`、`GridColumns`、`GridRows`、`PlacementMin`、`PlacementMax` 作为生成规则的单一来源，不另造第二套地形概率表。
- 新建可在检查器编辑的内容表现配置 `Resource`：`ItemScene`、地形物理层与阻挡开关、掉落物理层固定为 `0`、交互命中层、散射半径、散射时长、拾取飞行时长。
- 新建动画配置 `Resource`：`IdleDuration`、呼吸缩放幅度、明暗幅度、`HoverDuration`、挤压/拉伸倍率和回弹倍率。场景脚本可有 `@export` 的配置资源与必要的本地覆盖项，但不能让资源和代码各自维护一份互相矛盾的默认值。
- 所有新增 `Resource`、`@export`、公共方法和非直观顺序使用中文 `##` 说明用途、单位、默认值、覆盖关系及返回值。运行状态不能写回被多个房间共用的 `.tres`。

## 7. 仅本次运行与跨重启切换

一个局内快照结构同时服务两种模式。`RunPersistenceMode` 是检查器可选配置：`SESSION_ONLY` 为默认，`DISK` 为跨重启；运行时 `set_mode(mode)` 可切换，不通过玩家可见 UI。模式选择本身是偏好而非局内进度：首次启动取导出资源默认值，运行时切换后把选择写入现有 `SettingsManager`，下次启动先读取此选择再决定是否应用 `run` 快照。切换只改变写盘与下次启动恢复策略，当前内存中的地图和房间状态不重置。

`SESSION_ONLY`：权威状态留在 `Main/RuntimeState` 及局内协调器内存；`SaveManager` 继续写 `global`，但不把当前局内 `run` 快照写盘，也不在启动时应用旧的 `run` 快照。`DISK`：以同一份内存快照写 `run`，自动存档并在下次启动时恢复。运行时从内存模式切到磁盘模式时先取当前完整快照再写盘；切回内存模式时保留正在玩的状态，暂停局内写盘。若磁盘上已有旧快照，切回磁盘模式以**当前内存**覆盖旧快照，避免旧状态突然覆盖玩家眼前的局面。局外 `global` 永不受切换影响。

现有 `SaveManager.capture()` / `save_now()` 会把全部已注册 `run` 参与者写进主文件，因此实施时必须增加明确的写盘/读档门禁；不能只增加 `run` 参与者。内存模式下刷新 `global` 时保留磁盘中已有的旧 `run` 快照，但不写入当前本局状态，也不应用旧快照；再次切到磁盘模式才用当前内存状态覆盖它。要保证旧主存档的 `global` 内容、备份与原子写入行为不变。`project.godot` 当前还把 `SaveManager` 排在其他参与者之后，与现行“注册即应用”的规范冲突；实施阶段须先核对现有参与者的实际初始化时序，再调整 autoload 顺序和对应契约测试，不能假定注册会自动补发数据。

局内序列化只写稳定 ID、数值、坐标数组及纯字典，不写 `Node`、运行时 `Resource` 对象或整棵场景树。地形可通过房间场景的 `terrain_profile`、池条目索引和 `CardId` 校验恢复，嵌套子资源不能假定有独立文件路径；物品按现有 `CardId` 查表。无效或已删除的配置要告警并跳过单项，不能让整局静默变成新地图。

可恢复快照至少覆盖：随机地图格子与连接、起始/当前房间、玩家世界位置、地形实例全字段、掉落记录、建筑记录及其策略状态、游戏总时间、玩家本局库存。等级/经验/属性分配若被本局规则使用，也必须作为一个一致的玩家局内快照恢复，不能只保存等级。恢复顺序固定为：读取模式和快照 → 建立地图布局与房间坐标 → 恢复局内仓库/时间/玩家数据 → 创建 3×3 场景与内容 → 开放输入。继续本局时 `RunStartInitializer` 跳过“清空背包并消耗带入栏”的新局初始化；开始新局时清空旧 `run` 快照并正常执行带入。

用户已确认战斗中退出只恢复进入战斗前的世界快照。进入战斗前同步生成一次稳定快照；战斗进行期间暂停局内快照写盘，局外 `global` 自动保存继续运行。胜负结算回到世界后，恢复局内快照写盘。退出时 `SaveManager` 的兜底保存也不得把战斗中间态覆盖战前快照。

## 8. 兼容、验证与回退

`BoardController` 对外生成/删除/查询和信号协议尽可能保留，旧 `BoardCardView.tscn` 可留作测试与逐步迁移的回退资源；主场景最终只绑定新的 `Item`。`UIRoomBoardPresenter` 继续负责当前房间 HUD/背景相关触发，但内容生成与九房生命周期移交给内容流送层。建筑服务和仓库继续拥有原规则，表现层改为按活动房间索引。发布前对跨语言迁移留下的 `call` / `has_method` 路径逐个做运行验证。

验证应覆盖九房同时存在与窗口外无节点、状态往返、碰撞掩码、鼠标输入、长按采集、库存满、快速重复点击、飞行中跨房、建筑拆除掉落、两种模式往返和跨重启恢复。所有 `.gd` / `.tscn` / `.tres` 改动通过已打开的 Godot 4.7.1 编辑器 MCP 扫描、`tests/godot/` 套件、`Item.tscn` 与 `Main.tscn` 冒烟；最后只停止游戏，不关闭编辑器，并重查 Git 状态。阶段性回退按“存档门禁 → 内容流送 → 主场景接线”逆序进行，保留原场景资源直至新链路通过验证。
