全部步骤完成，验收在两层分别取得证据：

- 编辑器契约测试：`attribute_allocation_popup_contract` 10/10、`attribute_summary_ui_contract` 10/10；全量回归 328 通过 / 0 失败 / 42 套件。
- 真实游戏进程（必须先打开背包触发 `InventoryUI.Open` 的绑定，这是摘要拿到属性组件的前提）：
  - 有点数时「分配」按钮可见，`AvailablePoints` 变化驱动其显隐。
  - 点击按钮弹出弹窗，显示「可用点数：6」，物攻行显示当前值 `100`。
  - 连点两次 `+1` 后行内显示 `100 → 150`，而属性组件仍为 `100`、可用点数仍为 `6`——**累计阶段确实零写入**。
  - 点「确认」后物攻变为 `150`、可用点数 `6 → 4`、弹窗关闭——**确认才写入**。

### 过程中踩到的坑

1. `PopupPanel` 属于 `Window` 而非 `Control`，没有 `custom_minimum_size`，只有 `min_size`；误用会让整批 `batch_execute` 原子回滚。
2. 非 `@tool` 的 UI 脚本经**场景实例化**只会得到占位实例，连 `_ready` 都调不动；契约测试必须用「脚本 `new()` + 手工子树」构造夹具，生产场景的形状另用只读断言锁定。
3. 用 `脚本.new()` 构造的节点在 `add_child` 时**引擎已经自动调用过 `_ready`**，夹具再显式补调一次就成了第二次；因此 `_ready` 里的 `connect` 与行生成都必须幂等，否则行数翻倍、值标签引用被第二批覆盖（表现为界面值永远停在占位符）。
4. 「弹窗确实被关掉了」这类断言必须先让弹窗真正可见，否则在从未显示的状态下会无意义地通过。

### 验收后的两处修正

1. **弹窗一进游戏就浮在屏幕上**：新建场景时编辑器把 `PopupPanel` 的 `visible = true` 序列化进了 `.tscn`（既有 `AttributeDetailsPopup` 没有这行，所以一直正常）。除了删掉那行，`_ready()` 里还加了无条件 `hide()` 兜底——不同实例化路径下 Window 的默认可见性并不一致，不能只靠场景文件。契约侧新增「生产场景不得包含 `visible = true`」与「构造后 / 仅 Bind 后必须保持隐藏」两条断言。
2. **「可用点数」改为「剩余可分配点数」并实时变动**：原文案显示的是组件里的点数总量，而累计阶段不写入组件，玩家点 `+1` 后数字纹丝不动。改为显示 `可用点数 − 累计量`，点 `+1` / `-1` 立即增减（运行时实测 3 → 2 → 1 → 0，撤回回升到 1）。
3. 顺带修掉一个真实缺陷：`OpenFor` 对**同一个**组件重复打开时，`Bind` 会走「重复绑定」分支保留状态，导致上一次的残留累计被带进新一次分配。现在 `OpenFor` 无条件清空累计，并由 `test_popup_stays_hidden_until_opened` 锁定。

### 属性名回显已投入点数

属性名后回显该属性已投入的点数：`物攻（2）`，累计时变 `物攻（2→3）`。数据源是 `GetAttribute(type).AllocatedPoints`，只读显示，不参与写入。

实现这一条时又暴露出一个真实缺陷：`_on_confirm_pressed` / `_on_cancel_pressed` / `_on_popup_hide` 都是 `_pending.clear()` 后只调 `hide()`，**依赖 `hide()` 触发 `popup_hide` 来刷新**。窗口本来就不可见时 `hide()` 根本不发这个信号，界面会停在累计态（名称与值仍是 `(x→y)`）。现在三处统一走 `_discard_pending()`（清空 + 立即刷新），由 `test_name_column_echoes_allocated_points` 的「确认后落定为新的 x」断言锁定。

运行时实测：五行初始 `物攻（0）/物防（0）/法强（0）/法抗（0）/速度（0）` → 两次 `+1` 后 `物攻（0→2）` 且 `法强（0）` 不受影响 → 确认后落定 `物攻（2）`、属性值 100 → 150 → 重新打开仍为 `物攻（2）`。
