# 轮回结算系统

玩家死亡、明确通关或主动结束本局时，先停止当局，再把已经确定的收获放进局外仓库，最后显示 `scenes/GameProcess/Settlement.tscn`。面板只展示结果；重复打开、返回菜单和继续下一把都不再次发奖。当前正式可轮回资源名单为空，普通背包物品不会自动带出。默认开启死亡测试赠品，每局死亡赠送 1 个真实小麦。

## 数据由谁负责

| 模块与路径 | 当前职责 |
| --- | --- |
| `core/gameflow/run_session_data.gd` | 本局的内存账本：编号、活跃时长、统计、描述、开局收获容量、真实收获堆叠；不访问节点或文件 |
| `core/gameflow/run_snapshot.gd` | 世界快照：地图、房间、玩家位置、时间和背包；保留原采集/恢复协议，生产轮回流程禁止恢复旧局 |
| `core/progression/player_profile.gd` | 局外纯数据：金币、独立轮回代币、永久升级等级、收获容量、已入账编号、待领取溢出 |
| `core/save/save_manager.gd` | 持有唯一生产 Profile、读写/备份存档、统一控制玩法磁盘写入；自身适配 `player_profile` 存档键 |
| `core/autoloads/player_wallet.gd`、`core/progression/player_progression.gd` | 保留旧金币和容量升级接口及信号，内部读写 SaveManager 的同一 Profile |
| `core/gameflow/settlement_manager.gd` | 持有唯一当局账本，提供资格、选择、结算、重试、领取与导航入口 |
| `resources/save/settlement_config.gd` 与同名 `.tres` | Inspector 配置持久化、死亡赠品和正式资格名单 |
| `core/ui/settlement/` | 根协调器、收获区、统计/描述区、按钮区；不计算、不发奖、不直接写文件 |

`RunSessionData` 和 `RunSnapshot` 的区别：前者回答“这一局玩了多久、准备带出什么”，后者回答“世界现在在哪里、是什么状态”。背包快照里有某物品，只能证明玩家持有它，不能证明它有轮回资格。统计也不会变成第二份可领取库存。

当前没有独立 `SettlementRules` 或 `SettlementResult` 类：资格与纯奖励计算放在配置，固定结果采用字典与隔离后的 ItemStack 副本。正式代币换算、死亡惩罚和永久加点费用尚未制定；Profile 默认 `tokens = 0`，默认计算增量也是 0，不自行发放代币。

## 开局到结算

1. `RunStartInitializer.Initialize()` 在消耗带入之前调用 `SettlementManager.begin_run()`。写入门禁先打开，再清理旧世界快照和建立新编号。
2. 复用原带入流程与 `TimeSystem.RestoreSnapshot(0, 1, false)`。初始化完成后调用 `complete_run_initialization()` 开始计时。
3. 成功拾取才调用 `record_resource()` 记录数量；失败不计数。记录只改内存，也不会把该资源自动加入收获。
4. 地图 `player_died` 与战斗 `battle_ended(false)` 都进入 `finish_run("death")`。普通战斗胜利仍回世界，明确整局通关才调用 `finish_run("win", ...)`。暂停菜单“退出游戏”调用 `finish_run("abandon", ...)`。
5. 死亡赠品开启时，结果生成前调用统一 `add_harvest_item()` 添加 1 个配置物品；随后冻结账本、暂停世界，固定当局结果。
6. 调用配置的 `calculate_rewards(harvest, statistics, reason)` 生成真实堆叠副本与代币增量，再按 `run_id` 去重，只入账一次。每份堆叠通过 `GlobalWarehouse.AddItemStack()` 入库；放不下的部分存入 Profile 待领取，非负代币增量合入 Profile。清空已结束局快照后解除写入门禁。
7. 正式模式保存整份玩法存档；测试模式只更新内存。保存失败留在结算页，“重试保存”只重写同一份结果，不再次添加奖励。
8. 返回菜单进入 `scenes/main_menu_scenes/login_menu.tscn`；继续下一把进入新的 `scenes/Main.tscn`，编号、账本、时长、快照与时间重新初始化。

计时单位为实际秒，排除 `SceneTree.paused` 的时间，包括暂停菜单、开局抽卡等暂停。计时在初始化完成后开始、结算时停止；它与行动推进的昼夜 `TimeSystem` 分开。

整局结束后，世界协调器在异步战斗过场前后检查结束状态，跳过普通回世界、输入恢复和自动保存链，防止旧回调接管结算。

## Inspector 开关

在 Godot 文件系统选中 `res://resources/save/settlement_config.tres` 编辑。SaveManager 的 `SettlementSettings` 与 SettlementManager 的 `config` 默认共享这份资源。

| 字段 | 默认值与单位 | 生效规则 |
| --- | --- | --- |
| `persistence_enabled` | `false`，布尔开关 | 进程启动时锁定，修改后重新运行；关闭时本进程不写玩法存档 |
| `enable_death_test_reward` | `true`，布尔开关 | 仅死亡结果生成时读取；不影响通关、主动结束或正式资格名单 |
| `death_test_item` | `res://items/items/wheat.tres` | 每局死亡数量固定 1 个，走真实收获入口 |
| `allowed_resources` | 空 `Array[Resource]` | 正式资格按物品资源身份比较；普通小麦不会因为测试赠送而获得资格 |

两个开关独立：关闭持久化仍能在结算页和局外仓库看到真实赠品，并在同一进程继续带入、交易；重启后回到磁盘里的旧资产。关闭赠品且正式名单为空时，死亡后的 5 个格子全部为空。

若收获容量已被其它奖励占满且小麦不能合并，统一添加会整笔拒绝，描述显示“测试奖励未生成：收获格已满或测试物品配置无效”。不会超容量塞入，也不会添加一份只显示、不入库的假赠品。

## 真实物品与满仓

正常收获和测试赠品共用以下路径：`SettlementManager.add_harvest_item()` → `RunSessionData.add_harvest_item()` → 固定结果 → `GlobalWarehouse.AddItemStack()`。收获按物品最大堆叠数量拆格；同一资源、相同洗炼属性才能合并。

规则扩展入口 `SettlementConfig.calculate_rewards(harvest: Array, statistics: Dictionary, reason: String) -> Dictionary` 返回 `{"harvest": ItemStack副本数组, "tokens": 非负整数增量}`；当前保持物品数量不变并返回 0 枚代币。未来规则可通过派生配置覆写纯计算，但不能在此访问节点、修改资产或写文件。经理将规则输出再复制成固定结果，`token_delta` 与物品、结算编号同一次入账；重试不重新计算。Profile 代币余额上限为 2147483647 枚，超量饱和到上限；先收窄增量再相加，避免极大整数输入溢出为负数。

`AddItemStack(stack) -> int` 只读取来源，返回没放进去的数量。入库保留物品 Resource 身份和洗炼属性、保留目标槽位对象，并复制属性字典，避免结果或来源被外部修改后污染仓库。结算展示也使用副本。

仓库放不下时，余量由 `PlayerProfile.pending_harvest` 的编解码入口保存，不静默丢弃。`SettlementManager.claim_pending_harvest() -> int` 在局外重新尝试入库，返回本次真正入库的物品总数；未放下部分继续保留。当前提供领取方法，尚无单独的领取界面。

结算格子展示本局收获，不能再次拖出、使用、装备、丢弃或领取。真实物品已在仓库或待领取列表，实际操作通过原局外系统完成，避免结果副本变成第二份资产。

## 收获容量与界面扩展

默认容量为 5 格，最小永久容量为 5；即使没有任何收获也生成 5 个 `item_slot1.tscn`。`Harvest/ScrollContainer/SlotGrid` 按容量生成格子，4 列布局，超过可视高度可滚动。格子复用背包名称、图标、数量、单选和 TooltipPanel 详情。

| 接口 | 用途与返回值 |
| --- | --- |
| `SettlementManager.get_harvest_capacity() -> int` | 进行中返回本局开局容量；局外返回 Profile 的下局容量；结算面板仍读取固定结果的本局容量 |
| `SettlementManager.set_harvest_capacity(capacity: int) -> bool` | 更新下局永久容量，要求至少 5 格；发 `harvest_capacity_changed(capacity)` 并请求受门禁控制的保存 |
| 面板 `get_harvest_capacity() -> int` | 读取显示容量，默认 5 |
| 面板 `refresh_harvest_capacity(capacity: int) -> bool` | 仅调整格子显示，不升级 Profile；容量不得遮蔽已有收获 |

本局在开局固定容量，进行中或结算后改永久容量都不会修改已经确定的本局奖励。未来升级玩法应调用经理的永久容量入口，新局读取更新值；本期没有升级按钮、费用或每级增加值。

`Settlement.tscn` 根脚本提供以下公开接口；可以在进树前设置，无需访问内部标签：

| 方法 | 参数与效果 |
| --- | --- |
| `set_result(result: Dictionary) -> void` | 绑定固定结果，不发奖 |
| `set_play_time(seconds: float) -> void` | 设置展示秒数，负值显示为 0，格式 `时:分:秒` |
| `set_ending(id: String, title: String) -> void` | 设置结局编号与标题 |
| `set_description(text: String) -> void` | 替换全文 |
| `add_description(text: String) -> void` | 原文非空时换行追加；原文为空直接写入；空追加忽略 |
| `set_statistics(data: Dictionary) -> void` | 存储隔离的扩展统计，不直接显示机器键、不重新计算奖励 |
| `request_navigation(destination: String) -> bool` | 请求 `menu` 或 `next_run`，处理中或有错误时拒绝 |

局内事件希望描述进入最终结果，应调用 `SettlementManager.set_description()` / `add_description()`；结算页上的同名方法只调整显示。

```gdscript
# 先记录原文，再追加后续事件；最终保留两行。
var manager: Node = get_node("/root/SettlementManager")
manager.call("set_description", "击败了小怪1")
manager.call("add_description", "击败了boss1")
```

## 未来选择建筑的接口

本期没有建筑本体或选择界面，也不提前决定物品何时离开背包、取消时退到哪里。经理保留以下公开接口，选择和取消都明确返回失败，不改变库存或收获；后续建筑不直接写 Profile、仓库或存档，也不操作 Settlement 的节点。

| 方法 | 参数、返回与实际语义 |
| --- | --- |
| `can_reincarnate(item: Resource) -> bool` | 正式名单查询，目前对普通资源返回 false |
| `try_select_reincarnation_item(source: Node, slot_index: int, amount: int) -> Dictionary` | 来源需实现 `Capacity`、`GetStackAt`；只查询来源并验证进行中状态、基础入参及正式资格；有效请求仍返回 `{"ok": false, "error": "轮回选择建筑尚未接入，物品未移转"}` |
| `try_remove_reincarnation_item(selection_id: String, amount: int = -1) -> Dictionary` | `-1` 预留为取消全部；只验证进行中状态、非空编号与数量；有效请求仍返回未接入错误，无副作用 |
| `get_reincarnation_selection() -> Array` | 当前始终返回空的独立数组，尚无建筑选择记录 |
| `get_remaining_harvest_slots() -> int` | 进行中返回空格数，已结束返回 0；已有堆叠的余量仍由添加校验计算 |

后续建筑开发必须补齐来源数量、格子容量、选择编号与重复请求检查，并确定实际移转、取消归还和来源失效规则。只有这些规则确定后才能让接口返回成功；重复操作不能复制或丢失物品。

`add_harvest_item(item, amount, rolled)` 是已经授权的领域奖励入口，供正常奖励和测试赠品共用；建筑不得用该方法绕过资格查询或复制背包物品。

## 持久化与兼容

| 场景 | 玩法文件行为 |
| --- | --- |
| 测试模式 | 可读原存档；主档、备份、临时档、损坏现场均不修改；退出兜底保存也被拒绝 |
| 正式模式局外准备 | 沿用数据变化触发的 0.5 秒防抖保存 |
| 正式模式进行中 | 所有玩法写入暂缓，包括带入消耗、拾取、战斗保存请求、旧 DISK 模式和退出兜底 |
| 正式模式结算 | 仓库、Profile、旧钱包/升级键和空的 `data.run` 一起提交；失败可重试 |

存档格式版本仍为 1，旧 `warehouse`、`carry`、`player_wallet`、`player_progression` 键保持兼容，新增 `global.player_profile` 保存代币、未来等级、容量、已结算编号和待领取收获。金币和两个旧容量等级只由旧键编码，水合到同一 Profile，避免两个可写真相来源。

SaveManager 必须是 autoload 第一项，加载后同步水合参与者。生产轮回下 `RunSnapshot` 在自身就绪时就忽略旧快照，`begin_run()` 再显式清理；不能等新局已经恢复地图/背包后才清理。已结束局保存时不重新采集仍在树里的旧快照。

强制关闭窗口或编辑器停止运行发生在结算之前时，本局收益与带入消耗都不落盘；重启从上次已保存的局外资产开始，本局放弃，不恢复世界。`SESSION_ONLY` / `DISK` 保留用于旧快照协议，但不能绕过当前轮回的门禁。按键、音量等偏好继续使用 `user://settings.cfg`，不在玩法存档门禁范围内。

## 验证入口与待开发内容

纯数据与文件契约套件：`run_settlement_flow`、`settlement_persistence_contract`、`settlement_warehouse_contract`、`save_system_contract`，均通过 `tests/` 顶层壳发现。动态节点和 UI 生命周期必须通过 Godot 4.7.1 编辑器 MCP 的 `Settlement.tscn` 与 `Main.tscn` 冒烟验证，不能仅凭静态测试判断。

运行验证应覆盖：五格空状态、描述追加、物品选中和提示、真实死亡赠品入库、重复事件不发两份、通关/主动结束不赠品、满仓保留、失败保存重试、暂停时长排除、返回菜单和全新下一局、测试模式文件字节与写入计数不变。正式写盘只用 `user://test_...` 独立测试档验证，不覆盖真实玩家存档。

后续开发内容：正式可轮回资源与奖励换算、永久加点玩法、收获容量升级、选择建筑与交互界面、待领取界面。规则数值的权威汇总见 [游戏机制与玩法内容](游戏机制与玩法内容.md)。
